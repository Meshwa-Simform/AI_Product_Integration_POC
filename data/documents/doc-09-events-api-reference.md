# Events API Reference

The Events API is how your application publishes events to Loopwire and inspects what happened to them afterwards. All endpoints live under `https://api.loopwire.dev/v1` (or `https://api.eu.loopwire.dev/v1` for EU-region projects) and require an `Authorization: Bearer <key>` header.

## POST /v1/events — publish an event

Publishes a single event. Delivery to subscribers happens asynchronously after the request is accepted.

**Request body**

| Field | Type | Required | Notes |
|---|---|---|---|
| `type` | string | yes | Event type name, e.g. `order.created`. Must match `^[a-z0-9_]+(\.[a-z0-9_]+)+$`, max 64 characters. |
| `payload` | object | yes | Arbitrary JSON object, max 256KB. |
| `idempotencyKey` | string | no | Deduplicates retries of the same publish for 24 hours. Max 255 characters. |

```
POST /v1/events
Authorization: Bearer lw_live_xxx
Content-Type: application/json
Loopwire-Version: 2026-01-15

{
  "type": "invoice.paid",
  "payload": { "invoiceId": "inv_881", "amount": 12900, "currency": "usd" },
  "idempotencyKey": "invoice-paid-inv_881"
}
```

**Response — `202 Accepted`**

```
{
  "eventId": "evt_7Hq2kLm9",
  "type": "invoice.paid",
  "status": "accepted",
  "createdAt": "2026-03-04T09:12:44Z"
}
```

A `202` means the event has been durably stored and counted against your monthly quota. It does *not* mean any subscriber has received it yet — delivery typically happens within 500ms.

**Idempotent replays.** If you repeat the request with the same `idempotencyKey` and an identical payload within 24 hours, you get the original `eventId` back with `202`, and the event is not published a second time (and not counted twice). Same key with a different payload returns `409 Conflict`.

**Errors**

- `400 Bad Request` — invalid JSON, missing `type` or `payload`, invalid event type name, or payload larger than 256KB.
- `401 Unauthorized` — missing, invalid or revoked key.
- `402 Payment Required` — monthly event quota exhausted. Retrying won't help.
- `403 Forbidden` — project suspended, key scoped to a different event type, read-only key, or source IP not allowlisted.
- `409 Conflict` — idempotency key reused with a different payload.
- `429 Too Many Requests` — rate limit exceeded; wait for `Retry-After`.
- `500 Internal Server Error` — retry with exponential backoff (max 5 attempts total).

To publish many events at once, use `POST /v1/events/batch` (see Batch Publishing).

## GET /v1/events/{eventId} — retrieve an event

Returns the event, its payload, and a summary of delivery state across subscribers.

```
{
  "eventId": "evt_7Hq2kLm9",
  "type": "invoice.paid",
  "payload": { "invoiceId": "inv_881", "amount": 12900, "currency": "usd" },
  "createdAt": "2026-03-04T09:12:44Z",
  "deliverySummary": { "delivered": 2, "retrying": 1, "failed": 0, "skipped": 0, "pending": 0 }
}
```

Events older than the retention window (30 days on Free/Growth, 90 days on Scale) return `404 Not Found` — the payload has been permanently deleted.

## GET /v1/events — list events

Cursor-paginated list of events, newest first.

| Query param | Notes |
|---|---|
| `type` | Exact event type filter, e.g. `order.created`. |
| `created_after` / `created_before` | ISO-8601 timestamps. |
| `limit` | Default 20, max 100. |
| `starting_after` | Cursor from a previous response's `next_cursor`. |

Response shape: `{ "data": [...], "has_more": true, "next_cursor": "evt_..." }`. Payloads are omitted from list results to keep responses small; fetch an individual event to see its payload.

## GET /v1/events/{eventId}/deliveries — list deliveries

Returns one delivery record per subscriber that the event was routed to, each with a `dlv_...` ID, `subscriberId`, `status` (`pending`, `delivered`, `retrying`, `failed`, `skipped`), `attempts` (1–6), `lastResponseStatus`, and `nextAttemptAt` when retrying.

## POST /v1/events/{eventId}/redeliver — redeliver

Manually redelivers an event within the retention window. Body is optional: `{ "subscriberId": "sub_..." }` limits redelivery to one subscriber; omit it to redeliver to every subscriber the event originally matched. Redelivery resets that delivery's retry counter and does **not** count as a new event against your quota. Returns `202 Accepted`.

## Test mode

Requests made with a `lw_test_...` key hit the same endpoints but deliver to the dashboard's test inbox instead of real subscribers. Test events never count toward the monthly quota and are listed separately from live events — a live key cannot see test events and vice versa.

## Gotchas

- `eventId` values are generated by Loopwire; you cannot supply your own. Use `idempotencyKey` to correlate with your internal IDs.
- A `202` for a publish made while every matching subscriber is paused still counts toward quota, even though the deliveries end up `skipped`.
- Request bodies over 256KB are rejected before quota is checked, so an oversized payload never consumes quota.
